# xsd2poet Foundations

This document describes the fundamental abstractions, responsibilities, and
design principles of xsd2poet.  
Its purpose is to provide coding agents with the conceptual knowledge required
to understand, maintain, and extend the library.

## Purpose and architecture

xsd2poet generates a fluent Java API and an idiomatic Kotlin DSL for HTML from
an XML Schema Definition (XSD).  
The bundled `html_5_2.xsd` is the schema input used by both generators.

The project has three cooperating modules:

- `xsd2poet-core` parses XSD and exposes the in-memory schema model used by
  code generation.
- `xsd2poet-java` generates Java HTML element classes, interfaces, enums, and
  supporting infrastructure.
- `xsd2poet-kotlin` builds on the classes generated by `xsd2poet-java` and
  generates Kotlin extension functions and properties over that Java API.

The generation pipeline has three conceptual stages:

1. Load an XSD resource as an `InputStream`.
2. Parse the schema into typed model objects.
3. Translate those models into source using JavaPoet or KotlinPoet.

The Java and Kotlin modules each provide a `Main` entry point that loads the
bundled schema, invokes the shared parser, and runs its corresponding
generator.  
The Kotlin-generated extensions target the Java element classes and
interfaces, so the Java-generated API is the foundation of the Kotlin DSL.
Generated sources are written under each module's `target/generated-sources`
directory during the Maven build; they are build outputs rather than the
hand-maintained source of truth.

## Schema parser and model

`org.xmlet.newParser.Parser` is the boundary between the XML document and the
generators.  
It uses the JDK DOM APIs to walk schema nodes and stores recognized
declarations in separate collections:

- `ElementXsd` represents an HTML element, its attributes, referenced groups,
  choices, and child-sequence information.
- `AttrGroup` represents an XSD attribute group, including its attributes and
  references to other attribute groups.
- `Choice` and `Group` represent permitted element alternatives and reusable
  schema groups.
- `SimpleType` represents a restricted simple type, including its
  enumerations.
- `ElementComplete` carries information used to generate helper types for
  elements with sequence content.

These are schema models, not generated HTML nodes.  
They retain names, type names, and references in forms that the generators
can map into Java and Kotlin declarations.  
`BaseObject` provides shared naming and reference behavior, while
`BaseObjectWithAttrs` adds ordered attribute/type pairs.

The parser deliberately recognizes particular XSD constructs used by the
bundled schema, including elements, complex types, sequences, groups,
attribute groups, choices, `all` groups, and simple-type restrictions.  
When extending schema support, update the parser model and both affected
generators as needed; do not assume that an XSD construct is handled merely
because it is valid XML Schema.

## Generation and DSL shape

The Java module uses JavaPoet.  
Its `ClassGenerator` coordinates generation of element classes, choice and
group interfaces, attribute-group interfaces, simple-type enums, helper
classes, and visitor infrastructure.  
The checked-in Java sources under `org.xmlet.htmlapifaster` provide the
hand-maintained runtime and base types that the generated classes build on.

The Kotlin module uses KotlinPoet.  
Its `ClassGenerator` emits the `Xsd2PoetExtensions` source file, while
`ExtensionsGenerator` defines extension properties for elements and
extension functions for choices and groups.  
These extensions use the generated Java element types to support Kotlin
receiver-lambda DSL calls; they do not define a separate set of HTML element
classes.

Both generators depend on consistent model naming and reference resolution.  
Schema names are converted into generated class and method names.  
The Java generator maps XSD attribute types to JVM types or generated
enumeration types; the Kotlin extensions wrap the corresponding generated
Java API.  
When adding or changing a schema feature, preserve the generated API's fluent
element/parent relationships and keep Kotlin extensions consistent with the
Java API.

## Extension points and change guidance

- To change how schema declarations are interpreted, start in
  `xsd2poet-core` and its `org.xmlet.newParser` model classes.
- To change generated Java declarations, follow the orchestration in
  `xsd2poet-java`'s `ClassGenerator` into the relevant specialized generator.
- To change Kotlin DSL wrappers, follow `xsd2poet-kotlin`'s
  `ClassGenerator` and `ExtensionsGenerator`.
- Treat changes to generated Java element classes and interfaces as changes
  to the Kotlin DSL's underlying API; update or validate the Kotlin
  extensions when that API changes.
- To change the HTML vocabulary, update the XSD resource and verify that the
  parser and affected generators represent the changed declarations.
- Keep runtime support changes in the hand-maintained sources distinct from
  generated output.  
  Do not treat files under `target/` as the source to edit.

The module-specific Maven builds run their generators as part of the build
lifecycle.  
Use a clean build when validating generation changes so stale generated files
cannot hide missing or incorrect output.
